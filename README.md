## Problem

Freelancers and agencies that build websites need a steady pipeline of local businesses without a solid online presence. Finding them means opening Google Maps, scrolling feed after feed, manually noting names and phone numbers, then checking which ones lack a website — hours of repetitive work with copy-paste as the "pipeline." Search engines return noise, contact information is scattered across pages, and there is no clean way to turn discovery into an exported prospect list.

## Solution

LeadHunter discovers businesses in any niche and location, scrapes their contact details, and delivers them as ready-to-import contact files.

- Places search — scans Google Maps and keeps **every** business, tagged `has_website` so prospects without a site are obvious
- Web search — DuckDuckGo results are visited and contact pages probed for emails and phone numbers
- Persistent history — every run is stored in SQLite and survives restarts
- One-click exports — CSV, single vCards, full vCard sets, the whole database, and a complete history CSV
- Live dashboard — session counts, phone-rate metrics, and recent activity streamed from the backend

## Architecture

- **Web UI** — React SPA with routes for landing, dashboard, search, history, and settings; powered by TanStack Router, TanStack Query, motion, and Tailwind.
- **API server** — FastAPI exposes health, stats, search orchestration, session storage, and download endpoints; CORS enabled for the SPA.
- **Places provider** — defaults to a keyless Google Maps scrape loop (Playwright); switches to the official Google Places API when `GOOGLE_PLACES_API_KEY` is set.
- **Web scrape pipeline** — DuckDuckGo results are filtered, probed, and scraped by a 4-worker pool with per-host politeness; emails and phones are normalized and de-duplicated.
- **Persistence** — a thin SQLite layer (`database.py`) stores sessions plus their result payloads; location is configurable via `ODIFY_DB_PATH`.
- **Local mirror** — the browser keeps recent results in `localStorage`, so dashboard and history stay readable when the backend is down.

## Key engineering decisions

- **Keyless Google Maps scraping with API fallback** — offers the niche-majority Google Places API route when a key exists, yet still works without one; trade-off: the keyless path needs Playwright browser binaries.
- **SQLite instead of a hosted database** — a single operator gets durable, restart-safe history with no services to run; trade-off: single-writer concurrency is not suited to multi-user scale.
- **`localStorage` mirror of sessions** — the app degrades gracefully when the backend is unreachable; trade-off: local and server history can diverge.
- **Polite, parallel web scraping** — a bounded 4-worker pool with per-host pacing reduces bans without serializing every request; trade-off: slower queues on very large result sets.
- **Dedicated `GET /health` endpoint** — avoids colliding with the SPA's root route (the dev proxy cannot forward `/`); trade-off: one extra endpoint to maintain.
- **Strict 404s for missing sessions** — routes return real HTTP 404 instead of `200 + "session not found"`, fixing broken downloads after a database reset.

## Installation

Prerequisites: Python 3.12+, Node.js 22+ (for the Vite/TS 6 toolchain), and `npm`.

1. Clone the repository:
   ```bash
   git clone https://github.com/Dev-with-Mouzan/Lead_Hunter.git leadhunter && cd Lead_Hunter
   ```
2. Backend — create a venv and install dependencies:
   ```bash
   cd server
   python -m venv .venv
   # Windows: .venv\Scripts\activate   |   Linux/macOS: source .venv/bin/activate
   pip install -r requirements.txt
   ```
3. Optional: enable keyless Google Maps scraping:
   ```bash
   playwright install chromium
   ```
4. Configure environment (optional — keyless mode and default DB path need nothing):
   ```bash
   cp .env.example .env   # set GOOGLE_PLACES_API_KEY and/or ODIFY_DB_PATH as needed
   ```
5. Start the API:
   ```bash
   uvicorn main:app --reload --port 8000
   ```
6. Frontend — in a second terminal:
   ```bash
   cd client
   npm install
   npm run dev
   ```
7. Open `http://localhost:5173`. The Vite dev server proxies `/search`, `/search-places`, `/health`, `/stats`, `/sessions`, `/download`, and `/config` to port 8000.

## API documentation

Interactive docs are auto-generated at `http://localhost:8000/docs` (OpenAPI). Main endpoints:

| Method | Path | Purpose |
| --- | --- | --- |
| POST | `/search` | Web search — form: `query`, `country`, `max_results` → `{session_id, results}` |
| POST | `/search-places` | Places search — form: `niche`, `location`, `max_results` → `{session_id, results}` |
| GET | `/health` | Health check → `{ok, app, database}` |
| GET | `/stats` | Aggregated totals + most recent sessions |
| GET | `/config` | Live provider/database configuration |
| GET | `/sessions/{session_id}` | Full session with results (404 when missing) |
| GET | `/download/csv/{session_id}` | One session as CSV |
| GET | `/download/vcard/{session_id}/{idx}` | One lead as vCard |
| GET | `/download/all-vcards/{session_id}` | All leads in a session as vCards |
| GET | `/download/db` | The entire SQLite database file |
| GET | `/download/all-history.csv` | Every lead from every session in one CSV |
| GET | `/delete-session/{session_id}` · `/clear-sessions` | History management |

## Deployment

LeadHunter deploys to a single Vercel project — the SPA build plus the FastAPI backend as one serverless function:

- **Infra** — `vercel.json` builds the client (`cd client && npm install && npm run build`), serves the output from `client/dist`, and routes every API path (`/health`, `/stats`, `/config`, `/search`, `/search-places`, `/sessions/*`, `/download/*`) to the Python function `api/index.py`. All other routes fall back to `index.html` (SPA).
- **Backend function** — `api/index.py` re-exports the FastAPI app; `api/requirements.txt` installs the runtime deps (Playwright is omitted — keyless scraping cannot run serverless).
- **Environment** — set `GOOGLE_PLACES_API_KEY` in the Vercel project so Places search uses the official API. `ODIFY_DB_PATH` defaults to `/tmp/odify.db` on Vercel (ephemeral; download the database from Settings → Database to back it up).
- **Verify** — `vercel dev` runs the function plus the static output locally; `vercel --prod` ships it.

The client talks to the API same-origin, so no `VITE_API_URL` is needed on Vercel.

## Limitations

- The keyless Maps scraper needs Playwright, which cannot run on Vercel serverless functions; set `GOOGLE_PLACES_API_KEY` so Places search uses the official API, or run the API containerized locally.
- DuckDuckGo scraping depends on the HTML results page remaining stable and can be rate-limited; no CAPTCHA handling is implemented.
- The product is single-user: no authentication, and CORS is open (`*`), so it should not be exposed directly to the public internet.
- Email/phone extraction is heuristic — some sites yield no contact info, and international phone normalization is US/CA-centric.
- On Vercel, SQLite history lives in the ephemeral `/tmp` filesystem, so history resets between cold starts unless exported; the database download endpoint is the escape hatch.
- No automated test suite exists yet on either server or client.

## Future improvements

Prepared but not yet shipped, most impactful first:

- Add a Playwright-capable host/worker so keyless Places search works when `GOOGLE_PLACES_API_KEY` is not set.
- Add API-token auth, per-user history isolation, and CORS restriction.
- Stream search progress over SSE/WebSocket instead of a blocking request.
- Global lead dedupe and suppression by email/phone across sessions.
- Automated tests (`pytest` on the API, Vitest + Testing Library on the client) wired into CI.
- Broader international phone/country support and a richer contact-format export (XLSX, direct CRM sync).
